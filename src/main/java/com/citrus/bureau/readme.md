# 1. module定義
這個module主要用途是：外部資料源的防腐層 (Anti-Corruption Layer)，負責標準化所有第三方數據。包含打小報告用

# 2. 核心邏輯
核心邏輯：
    PAN 驗證：檢查稅號有效性與持有人姓名一致性。
    CIBIL 查詢：獲取信用分數、歷史違約紀錄 (Tradelines)。
    BSA 解析：解析銀行流水 (Bank Statement)，計算 FOIR (償債能力比)。
    快取策略：實作 Caching 機制 (e.g., 30 天內不重複查詢)，節省成本。

---

# 3. 需求文件

## 3.1 這個模組在做什麼？(業務背景)

在印度貸款流程中，放款前必須「徵信」—— 也就是調查申請人的信用狀況。  
這個模組就是專門去對接各種**第三方數據供應商**，把他們回傳的雜亂資料**標準化**，讓後面的 `origin` 模組可以直接拿來決策。

**白話說：** 這是貸款系統的「偵探部門」，負責去查申請人的底細。

### 為什麼需要這個模組？

1. **第三方 API 格式不統一** — 每家供應商的回應格式都不同，需要有人統一翻譯
2. **查詢要錢** — 每查一次 CIBIL 可能要 ₹20-50，需要快取避免重複查
3. **合規要求** — 印度 RBI 規定必須留存查詢紀錄，需要統一記錄

---

## 3.2 主要功能清單

| # | 功能名稱 | 說明 | 優先級 |
|---|---------|------|-------|
| 1 | **PAN 驗證** | 驗證印度稅號(PAN)是否有效、姓名是否一致 | P0 |
| 2 | **CIBIL 信用查詢** | 取得信用分數(300-900)、歷史借貸紀錄 | P0 |
| 3 | **BSA 銀行流水分析** | 解析銀行流水，算出月收入、現有負債、FOIR | P0 |
| 4 | **查詢結果快取** | 同一個人 30 天內不重複查詢，節省成本 | P0 |
| 5 | **綜合報告產出** | 把上述三種結果打包成一份標準報告 | P1 |
| 6 | **查詢紀錄留存** | 記錄每次查詢的時間、結果、成本（合規用） | P1 |

## 3.3 業務場景說明

### 場景 1：新貸款申請
```
用戶提交貸款申請
    ↓
origin 模組收到申請，呼叫 bureau
    ↓
bureau 依序執行：
    1. PAN 驗證 → 確認身份真實
    2. CIBIL 查詢 → 取得信用分數
    3. BSA 分析 → 確認還款能力
    ↓
bureau 回傳標準化報告給 origin
    ↓
origin 根據報告決定核准/拒絕
```

### 場景 2：重複申請（快取命中）
```
同一用戶 7 天前才申請過，又來申請
    ↓
bureau 檢查快取 → 命中！
    ↓
直接回傳快取資料，不用再花錢查
```

### 場景 3：供應商異常
```
CIBIL API 掛了
    ↓
bureau 重試 2 次
    ↓
還是失敗 → 回報錯誤，讓 origin 決定要不要用備援方案
```

## 3.4 建議 API 清單

| API | 用途 | 呼叫者 | 備註 |
|-----|------|-------|------|
| `POST /bureau/pan/verify` | 單獨驗證 PAN | origin | 可單獨使用 |
| `POST /bureau/cibil/inquiry` | 單獨查 CIBIL | origin | 需要用戶授權 |
| `POST /bureau/bsa/analyze` | 單獨分析銀行流水 | origin | 支援上傳檔案 or AA |
| `POST /bureau/report/full` | 一次做完全部，產出綜合報告 | origin | **最常用這個** |
| `GET /bureau/report/{orderId}` | 查詢既有報告 | origin, loancore | 給其他模組查閱用 |

## 3.5 大概會怎麼開發

### Step 1：先把外部 API 包起來 (防腐層)
- 為每個供應商寫一個 Adapter（例如 `KarzaPanAdapter`, `CibilAdapter`）
- 統一輸出格式，不管背後是誰提供的

### Step 2：做快取機制
- 用 orderId + panNumber + 查詢類型 當 key
- 設定 TTL（例如 30 天過期）
- POC 階段可以直接存 DB，正式可改 Redis

### Step 3：實作綜合報告
- 把 PAN + CIBIL + BSA 的結果組合起來
- 算出一個綜合風險分數（可以是簡單加權）

### Step 4：查詢紀錄
- 每次呼叫外部 API 都要記一筆 log
- 記錄：時間、花費、結果、錯誤碼

## 3.7 和其他模組的關係

```
            ┌─────────────┐
            │   origin    │  (審核模組)
            └──────┬──────┘
                   │ 呼叫
                   ▼
            ┌─────────────┐
            │   bureau    │  ◄── 你在這裡
            └──────┬──────┘
                   │ 呼叫外部 API
                   ▼
        ┌──────────────────────┐
        │  外部供應商 (CIBIL等) │
        └──────────────────────┘
```

**通訊建議：**
- `origin → bureau`：**同步呼叫**（審核流程需要即時結果）
- `bureau → loancore`：可選 **MQ 通知**（告知徵信完成，更新主狀態）

## 3.8 微服務切分點 (未來考量)

此模組是**天然的微服務邊界**，原因：
1. 與外部 API 強相依，掛了不應該影響其他模組
2. 成本敏感（每次查詢都要錢），需要獨立監控
3. 可以獨立限流、熔斷

**建議：** POC 先單體，上線前可優先把這個模組拆出去。

## 3.9 印度特有注意事項

| 項目 | 說明 |
|-----|------|
| **PAN 格式** | 10 碼，例如 `ABCDE1234F`（5字母+4數字+1字母） |
| **CIBIL 分數** | 300-900，750+ 算優良 |
| **用戶授權** | 查 CIBIL 前**必須**取得用戶同意，要記錄授權時間 |
| **FOIR** | Fixed Obligation to Income Ratio，通常要 < 50% 才會核貸 |
| **AA (Account Aggregator)** | 印度官方的銀行資料共享框架，比傳統 BSA 更即時 |
