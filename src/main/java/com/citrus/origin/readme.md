# 1. module定義
這個module主要用途是：自肥檢傷分類

# 2. 核心邏輯：
核心邏輯：
    流量清洗 (Filter)：執行 Dedupe (去重) 與黑名單過濾。
    策略引擎 (Strategy)：根據 Bureau 數據跑決策樹 (Decision Tree)。
    產品定價 (Pricing)：計算核准額度 (Limit)、利率 (ROI)、年期 (Tenure)。
    自肥判定：Pass -> 產出 Offer，進入 Sign。
    Reject -> 轉送至 LSP 模組。

---

# 3. 需求文件

## 3.1 這個模組在做什麼？(業務背景)

這是貸款系統的**大腦**，負責決定：
1. 這個人能不能借錢？
2. 能借多少錢？
3. 利率是多少？

所謂「自肥」就是這個案子我們自己做（賺利息）；「檢傷分類」就是把好案子留下來，壞案子轉給別人（LSP 合作商）。

**白話說：** 這是貸款系統的「審核官」+「定價師」。

### 為什麼需要這個模組？

1. **風控** — 不能把錢借給還不起的人
2. **利潤最大化** — 根據風險調整利率，風險高就收高利率
3. **流量變現** — 自己不想做的案子轉給合作商，還能收導流費

## 3.2 主要功能清單

| # | 功能名稱 | 說明 | 優先級 |
|---|---------|------|-------|
| 1 | **Dedupe 去重** | 同一人短期內重複申請，直接擋掉 | P0 |
| 2 | **黑名單過濾** | 在黑名單的人直接拒絕 | P0 |
| 3 | **決策引擎** | 根據徵信資料跑規則，決定 Pass/Reject/Review | P0 |
| 4 | **額度計算** | 根據收入、信用分數計算可貸額度 | P0 |
| 5 | **利率定價** | 根據風險等級決定利率 (ROI) | P0 |
| 6 | **產品匹配** | 根據額度和用戶需求匹配貸款產品（期數、類型） | P1 |
| 7 | **LSP 路由** | 自己不做的案子，選擇導給哪個合作商 | P1 |

## 3.3 業務場景說明

### 場景 1：優質客戶（自肥）
```
bureau 回傳徵信報告：
    - CIBIL 分數：780 (優良)
    - FOIR：35% (負債比低)
    - 無逾期紀錄
    ↓
origin 決策：
    - 判定：PASS
    - 核准額度：₹100,000
    - 利率：18% 年化
    - 期數：12 期
    ↓
origin 產出 Offer，通知 sign 開始簽約
```

### 場景 2：高風險客戶（拒絕）
```
bureau 回傳徵信報告：
    - CIBIL 分數：520 (差)
    - 有 3 筆呆帳紀錄
    ↓
origin 決策：
    - 判定：REJECT
    - 原因：CIBIL_TOO_LOW, WRITE_OFF_HISTORY
    ↓
訂單狀態 → REJECTED
```

### 場景 3：邊緣客戶（導流）
```
bureau 回傳徵信報告：
    - CIBIL 分數：650 (普通)
    - FOIR：55% (偏高)
    ↓
origin 決策：
    - 自己的風控政策不接受
    - 但是合作商 A 可能會接受
    ↓
origin 路由到 LSP 模組
    ↓
LSP 嘗試導給合作商
```

### 場景 4：重複申請（去重）
```
用戶 3 天前剛申請過，被拒絕了
    ↓
用戶又來申請
    ↓
origin 檢查 Dedupe → 命中！
    ↓
直接拒絕，不重新跑決策（節省徵信成本）
```

## 3.4 決策引擎規則 (範例)

這些規則由業務定義，這裡只是範例：

### 硬拒規則 (Hard Reject)
| 規則 | 條件 | 說明 |
|-----|------|------|
| R001 | CIBIL < 500 | 信用分太低 |
| R002 | 有呆帳 > ₹50,000 | 有大額呆帳 |
| R003 | 近 6 個月新增貸款 > 3 筆 | 疑似貸款堆疊 |
| R004 | 在黑名單中 | 不解釋 |

### 軟規則 (Scoring)
| 規則 | 分數影響 |
|-----|---------|
| CIBIL 750+ | +20 分 |
| CIBIL 700-749 | +10 分 |
| CIBIL 650-699 | 0 分 |
| CIBIL < 650 | -20 分 |
| FOIR < 40% | +15 分 |
| FOIR 40-50% | +5 分 |
| FOIR > 50% | -10 分 |
| 有穩定薪資 > 6 個月 | +10 分 |

### 額度計算公式 (範例)
```
核准額度 = 月收入 × (50% - FOIR) × 期數

例：
月收入 = ₹50,000
FOIR = 30%
期數 = 12

額度 = 50,000 × (50% - 30%) × 12 = ₹120,000
```

## 3.6 大概會怎麼開發

### Step 1：建立過濾器
- DedupeFilter：檢查重複申請
- BlacklistFilter：檢查黑名單
- 過濾器用 Chain of Responsibility 模式串起來

### Step 2：決策引擎
- 定義規則格式（可以用 JSON 或 DB 存規則）
- 實作規則執行器
- POC 可以 hardcode 規則，正式版再做規則引擎 UI

### Step 3：定價計算
- 根據風險等級決定利率
- 根據收入和 FOIR 計算額度
- 需要考慮最低/最高額度限制

### Step 4：產出 Offer
- 把決策結果包裝成 Offer
- 存入 DB，供後續流程使用

## 3.7 和其他模組的關係

```
            ┌─────────────┐
            │   bureau    │
            └──────┬──────┘
                   │ 徵信報告
                   ▼
            ┌─────────────┐
            │   origin    │  ◄── 你在這裡
            └──────┬──────┘
                   │
         ┌─────────┴─────────┐
         │                   │
         ▼                   ▼
   ┌─────────┐         ┌─────────┐
   │   sign  │         │   lsp   │
   │ (自肥)  │         │ (導流)  │
   └─────────┘         └─────────┘
```

**通訊建議：**
- `loancore → origin`：**同步呼叫**（審核是關鍵路徑）
- `origin → sign/lsp`：透過 **loancore 協調**，不直接呼叫

## 3.8 微服務切分點 (未來考量)

**可考慮獨立**，原因：
1. 決策規則可能頻繁變更，獨立部署可避免影響主服務
2. 可以對接外部決策引擎（如 Drools）
3. 不同產品線可能有不同審核邏輯

但 POC 階段建議先保持單體。

## 3.9 印度特有注意事項

| 項目 | 說明 |
|-----|------|
| **FOIR 上限** | 多數銀行要求 FOIR < 50%，否則不核貸 |
| **利率上限** | RBI 有規定的年化利率上限，要注意別超過 |
| **冷靜期** | 核准後用戶有權在特定時間內取消，需預留機制 |
| **多頭借款** | 印度常見問題，需檢查近期貸款申請次數 |
