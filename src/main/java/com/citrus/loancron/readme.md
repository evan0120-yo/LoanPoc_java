# 1. module定義
這個module主要用途是：所有outbox以外的排程, 批次排成支付, 包含冷靜期邏輯

# 2. 核心邏輯：
核心邏輯：
    日切 (EOD)：每日 00:00 觸發。
    計息觸發：發送 ACCRUAL_Run 指令給 Ledger。
    逾期檢測：掃描未還款訂單，更新 DPD (Days Past Due)。
    狀態遷移：觸發 Active -> Overdue -> NPA 的狀態改變。

---

# 3. 需求文件

## 3.1 這個模組在做什麼？(業務背景)

這是貸款系統的**定時鬧鐘**，負責每天或定時執行的背景任務。
最重要的是「日切」—— 每天凌晨要做的結算工作。

**白話說：** 這是貸款系統的「值夜班的人」，大家下班了它才開始幹活。

### 為什麼需要這個模組？

1. **日結計息** — 每天要算一次利息
2. **逾期檢測** — 每天要檢查誰沒還錢
3. **自動扣款** — 還款日要自動扣款
4. **狀態遷移** — 逾期天數達標要自動變 NPA

### 為什麼不用 Outbox？

Outbox 模式是用來確保資料庫和 MQ 的一致性。
但 loancron 處理的是**主動發起的**排程任務，不是事件驅動的，所以單獨處理。

| # | 功能名稱 | 說明 | 優先級 |
|---|---------|------|-------|
| 1 | **日切 (EOD)** | 每日 00:00 執行的結算任務 | P0 |

## 3.3 業務場景說明

### 場景 1：每日日切 (EOD Job)
```
時間：每日 00:00
    ↓
1. 計息
    - 發送 ACCRUAL_RUN 給 ledger
    - ledger 計算所有 ACTIVE/OVERDUE 訂單的日息
    ↓
2. 逾期檢測
    - 掃描所有 ACTIVE 訂單
    - 檢查今天是否有應還款項未還
    - 有的話 DPD +1
    ↓
3. 狀態遷移
    - DPD > 0 且狀態仍是 ACTIVE → 改成 OVERDUE
    - DPD > 90 → 改成 NPA
    ↓
4. 通知催收
    - 把今天新增的逾期訂單通知 callect
```

### 場景 2：自動扣款日
```
時間：每日 09:00
    ↓
掃描今天是還款日的訂單
    ↓
對每筆訂單：
    1. 查詢應還金額
    2. 呼叫 pay 發起 e-NACH 扣款
    3. 等待結果
    ↓
成功 → 走正常還款流程
失敗 → 發送 SMS 通知用戶手動還款
```

### 場景 3：冷靜期結束
```
印度 RBI 規定：借款人在放款後有 N 天冷靜期可以取消

時間：放款後第 4 天凌晨
    ↓
掃描冷靜期即將到期的訂單
    ↓
冷靜期結束，確認貸款生效
    ↓
正式開始計算利息
```

### 場景 4：簽約超時
```
時間：每日 02:00
    ↓
掃描狀態為 SIGNING 的訂單
    ↓
檢查簽約開始時間
    ↓
超過 7 天未完成 → 狀態改為 EXPIRED
```

## 3.4 DPD (Days Past Due) 說明

DPD = 逾期天數，從還款日開始計算

| DPD 範圍 | 分類 | 說明 |
|---------|------|------|
| 0 | 正常 | 按時還款 |
| 1-30 | B0 | 輕微逾期 |
| 31-60 | B1 | 中度逾期 |
| 61-90 | B2 | 嚴重逾期 |
| 90+ | NPA | 不良資產 (Non-Performing Asset) |

## 3.7 大概會怎麼開發

### Step 1：排程框架
- 用 Spring Scheduler 或 Quartz
- 定義 Cron 表達式

### Step 2：任務實作
- 每個任務一個 Job Class
- 支援重試和失敗處理

### Step 3：任務互斥
- 確保同一任務不會重複執行
- 用分散式鎖（如 Redis Lock）

### Step 4：監控告警
- 任務失敗要發告警
- 記錄執行時間和結果

## 3.8 和其他模組的關係

```
                   ┌─────────────┐
                   │  loancron   │  ◄── 你在這裡
                   └──────┬──────┘
                          │
         ┌────────────────┼────────────────┐
         │                │                │
         ▼                ▼                ▼
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │  ledger │      │loancore │      │   pay   │
   │ (計息)  │      │(狀態遷移)│      │(自動扣款)│
   └─────────┘      └─────────┘      └─────────┘
         │                │
         │                ▼
         │          ┌─────────┐
         │          │ callect │
         │          │ (催收)  │
         │          └─────────┘
         │
       結果
```

**通訊建議：**
- `loancron → ledger`：**MQ** (ACCRUAL_RUN)
- `loancron → loancore`：**MQ** (狀態變更)
- `loancron → pay`：**同步** (自動扣款需要即時結果)
- `loancron → callect`：**MQ** (新增逾期通知)

## 3.9 微服務切分點 (未來考量)

**強烈建議獨立**，原因：
1. 排程任務會消耗大量資源，不應影響主服務
2. 可以獨立擴展（多個 worker 並行處理）
3. 任務失敗不影響正常業務

---

## 3.10 重要設計考量

| 項目 | 建議 |
|-----|------|
| **冪等性** | 任務重複執行不會造成錯誤 |
| **分散式鎖** | 防止多實例重複執行 |
| **分片處理** | 大量訂單時分片並行處理 |
| **超時處理** | 任務執行太久要能自動終止 |
| **失敗告警** | 關鍵任務失敗要即時通知 |
